# 升学 AI 真实测速

`node tools/ai-performance.js baseline` 在改动搜索逻辑前保存原始实现快照与六次真实测试：指定山东大学、济南条件推荐各三次。`node tools/ai-performance.js optimized` 使用相同输入和配置复测；`node tools/ai-performance.js compare` 生成中位数对比报告。

这些命令调用现有 DeepSeek 接口，属于付费集成测试，不加入普通回归。普通回归使用模拟请求，不需要密钥或联网。不要输出配置文件、密钥、请求头或模型思考内容。

显式运行真实集成或性能测试前，请通过 `DEEPSEEK_API_KEY` 环境变量提供密钥；工具不再从项目文件读取内置密钥，也不读取浏览器保存的密钥。

结果在 `artifacts/ai-performance/`。每次结束立即落盘，记录成功、失败、实际搜索次数、最大并发、修复次数与各阶段时间。失败响应的可读文本和实际返回来源保存在诊断文件中，不记录私有思考块。首次测试无法联网的记录单独保存，不作为性能样本。

搜索耗时包含全部搜索请求和请求内部的思考。思考生成耗时从检索完成到计划校验通过或失败，包含一次允许的修复；不称为模型纯推理耗时。首条来源按能展示给用户的时点记录，因此会体现流式传输的改善。

仅成功样本进入性能中位数；任一版本某场景不足两次成功，不给出该场景可靠的提升百分比。必要时使用 `baseline --append --named` 或 `--local` 补测三次，保留全部失败记录；追加基线始终运行保存的原始实现。优化版本变化后先将旧的 `optimized.json` 和对应诊断文件另存，再复测，不能混合不同版本的数据。

报告公式：耗时下降百分比 = (优化前中位数 − 优化后中位数) / 优化前中位数 × 100%；加速倍数 = 优化前中位数 / 优化后中位数。负的耗时下降表示变慢，需要如实报告。

自动化验证：`node tools/dev.js test` 包含来源与计划校验、并发及流式协议、测速统计测试；`node tests/ai-browser.test.js` 验证 file/HTTP、390/1042/1440px 的交互与存储。

## 输入缓存对比

`node tools/ai-performance.js cache` 使用 `artifacts/ai-cache-performance/baseline-ai.js` 保存的优化前快照与当前实现，指定院校、按条件推荐两个场景各执行优化前后两次，版本交替执行，总计最多八轮真实生成。此命令消耗 DeepSeek 余额，不属于普通回归；不额外预热、不自动补测、不覆盖已有 `results.json`。认证、余额、访问或整体网络失败时提前停止。

报告单独保存在 `artifacts/ai-cache-performance/results.json` 和 `report.md`。逐请求记录原始 `usage`、归一化用量、阶段、任务、耗时及响应状态；不保存请求头、密钥、响应文本或思考内容。首次仅表示本次实测中的首次，不表示服务端冷缓存。此前页面截图的当天命中率约31.4%，是历史参考，不替代此次优化前实测。

输入命中率 = 命中输入 token ÷（命中输入 token + 未命中输入 token），整轮与阶段按 token 加权。DeepSeek 原生命中/未命中字段优先；Anthropic 用量的未缓存输入及缓存写入计入未命中输入，缓存读取计入命中输入。累计流式统计按字段覆盖合并，不累加多个更新。缺少缓存用量的请求标为不可用，零输入不计算比例，部分统计不代表完整生成。

应用提供可选 `StarPath.ai.generate(input, { onUsage })` 回调，每次完整响应调用一次，传入 `stage`、`taskId`（生成阶段为空）、检索 `round` 或生成 `attempt`、`inputTokens`、`cacheHitTokens`、`cacheMissTokens`、`outputTokens`、`cacheHitRate` 及 `rawUsage`。不把用量写入用户计划或 localStorage。

小样本只记录观察。两版本均成功且用量完整，输入命中率提高、未命中输入减少、请求数及输出量没有增加时，才标记该场景满足改善条件；失败及已取得用量也保留，不能只挑选成功记录。来源仍每次联网检索，模型、思考强度、动态搜索额度和并发数不因缓存优化改变。

## 计划生成提速对比

`node tools/ai-performance.js speed` 使用 `artifacts/ai-speed-performance/baseline-ai.js` 保存的提速前版本，与当前实现交替运行。指定院校、条件推荐两个场景分别做优化前后各两次，共最多八轮，消耗DeepSeek余额；不额外预热、不自动补测，不覆盖已有报告。

提速前后使用相同模型、输入、检索思考强度、搜索上限、并发数和超时。优化版仅将计划生成及一次允许的修复改为 `low`，使用学习行动字符串和来源编号，阶段、日期与实际网址由程序组装。计划生成仍为非流式请求；报告分别记录检索、计划生成（含修复）、完整生成和首条官方来源的耗时。

结果独立保存在 `artifacts/ai-speed-performance/results.json` 与 `report.md`。逐请求还记录实际思考强度、是否流式、生成返回格式（compact/full/invalid）及用量，不保存响应文本或思考。成功样本的中位数用于比较，不足两个成功样本不报告可靠加速比例；失败和输出用量保留。既有计划结构和全部校验继续兼容，通过验证代表原有结构与来源约束通过，不代表人工复核了每条事实。

## 并行学习行动与结构化院校核验

上述报告对应各自冻结版本。当前未指定院校的流程并行生成16项行动、逐校返回结构化事实、程序合并院校、最终只整合摘要及行动修改。请求共用最多8个槽位，搜索仍至少15次、最多18次；检索保持high，草稿和整合保持low。指定院校沿用六项检索和紧凑生成。

`node tools/ai-overlap-performance.js` 是显式付费命令：未指定院校基线和优化版各3次、指定院校各1次，最多8轮，版本交替，不预热、不自动补测、不覆盖已有报告。源码快照、哈希、输入、逐请求阶段与耗时、实际搜索数、并发、用量、失败和中位数保存在 `artifacts/ai-overlap-performance/`。不记录密钥、请求头、模型响应文本或思考。

搜索按开始至检索完成的墙钟时间计，行动草稿和最终整合分别计时。重叠是草稿请求与所有检索请求时间区间交集的并集，不能逐条相加并发搜索时间，也不能将检索与草稿的完整耗时相加当成总耗时。总耗时单独测量；成功样本的中位数至少各2个，且成功率不下降、耗时下降至少25%时才判定达到目标。指定院校各1个样本只作兼容观察。

首轮真实测试暴露地域核验失败后，修正版优先采用济南已有官方历史线索，并明确城市字段只填地级名称、区县放入校区说明。仍逐校联网核对实际专业培养地点，不放宽地域或历史层次校验。`node tools/ai-overlap-performance.js --revised` 显式执行修改后版本的3次条件推荐，复用完整首轮中相同源码、输入与配置的3次基线，输出到独立 `revised/` 目录。首轮失败样本完整保留，不能混入修正版性能中位数；复用基线存在服务时间波动影响。

`onUsage` 增加可选 `phase`（learning/integration/generation）；原stage、taskId和用量字段兼容。学习行动阶段不计最终修复次数，不写入用户计划或localStorage。新流程的阶段对比使用本节工具，旧缓存及speed工具不能据请求顺序区分并行草稿和最终整合。
